# Tiny Stories x SmolLM-Corpus (curriculum dataset)

A soft-curriculum dataset sub-project for the
[`small-llm`](../README.md) pretraining example. It interleaves
[`roneneldan/TinyStories`](https://huggingface.co/datasets/roneneldan/TinyStories)
with `HuggingFaceTB/smollm-corpus` such that early in training the
model sees mostly Tiny Stories and gradually transitions to
SmolLM-corpus, with no hard switch between the two.

This sub-project is the dataset half of the example pattern in the
parent project: training projects can point at it via `ns.dataset_proj`
/ `ns.dataset_config` (see
[`tiny_x_small_lm.yaml`](../templates/configs/tiny_x_small_lm.yaml) and
[`final.yaml`](../templates/configs/final.yaml)).

## Source datasets

- **TinyStories** ([Eldan & Li, 2023](https://arxiv.org/abs/2305.07759)):
  ~2.1M synthetic short stories generated by GPT-3.5 and GPT-4 using a
  small vocabulary, designed for training small models that produce
  coherent English. Pulled from
  [`examples/datasets/roneneldan/`](../../../datasets/roneneldan/) via
  the `fast-iter-packed.yaml` config (packed iterable variant with
  position-based checkpoint resumption). Acts as the "easy" early phase
  of the curriculum.
- **SmolLM-Corpus**: the same `smollm-corpus/interleaved-packed.yaml`
  used as the parent project's default training set - an interleaved
  mix of FineWeb-Edu-dedup and Cosmopedia-v2. Pulled from
  [`examples/datasets/HuggingFaceTB/`](../../../datasets/HuggingFaceTB/).
  Acts as the "real" target distribution.

Both source datasets are pre-tokenised and packed into fixed-length
sequences (default 4096 tokens, configurable via `--max-length`) so
that no tokens are wasted on padding.

## How the soft transition works

The two source datasets are merged with
`forgather.ml.datasets.interleave_datasets`, with the per-step sampling
weights provided by `forgather.ml.datasets.soft_sequential`. On every
draw, each dataset's weight is proportional to *the fraction of its own
examples that haven't been seen yet*, multiplied by the leftover
probability mass from all earlier datasets:

```
weight[i] = (remaining[i] / total[i])
          * product over j<i of (1 - remaining[j] / total[j])
```

For the two-dataset case used here, this means:

- **At step 0**, both datasets are untouched, so the *first* dataset
  (Tiny Stories) gets ~100% probability and SmolLM gets ~0%. Effectively
  all early samples are Tiny Stories.
- **As Tiny Stories drains**, its weight falls and SmolLM's leftover
  share rises. The transition is gradual, not a step function -
  there's no point at which the model "switches" datasets, only a
  smooth ramp.
- **After Tiny Stories is exhausted**, all subsequent samples come from
  SmolLM-corpus.

`stopping_strategy: "all_exhausted"` means the iterator continues until
*both* sources are fully consumed; combined with the weighting rule
above, this produces a single-pass curriculum where Tiny Stories
dominates early and SmolLM dominates late, with a smooth handoff in
between.

The exact shape of the transition is determined by the *relative sizes*
of the two source datasets: Tiny Stories is much smaller than
SmolLM-Corpus, so it drains faster and the SmolLM ramp completes within
a relatively small fraction of total training. There's no explicit
"transition midpoint" parameter - if you want a different shape, change
the size of one of the source datasets (e.g., subset SmolLM).

## Eval and test sets

`eval_dataset` and `test_dataset` come **only from SmolLM-corpus** -
the curriculum applies to training only. This is intentional: the
target distribution we care about is SmolLM, so eval loss measures
progress against the harder corpus regardless of where training is in
the curriculum.

A practical consequence is that any Tiny Stories-specific patterns the
model picks up that don't transfer to SmolLM never show up in eval
loss. So the eval-loss benefit of the curriculum (~0.020 in the parent
project's 10x runs) is plausibly a lower bound on its actual
contribution to mid-training generation quality.

## Configurations

```
forgather ls
```

| Config | Purpose |
|--------|---------|
| `default.yaml` | Soft-sequential interleave of Tiny Stories → SmolLM-corpus, packed at 4096 tokens. |

The default config is the only one currently shipped - all
configurability comes from CLI overrides at training time
(`--max-length`, `--stride`, etc.) and from the source-dataset
sub-projects.

## Usage from a training project

A training project consumes this dataset by pointing at it from a
config that extends the parent project:

```yaml
-- extends 'project.yaml'

[config_metadata]
    == super()
    -- set ns.dataset_proj = abspath(joinpath(project_dir, 'tiny-stories_small-lm'))
    -- set ns.dataset_config = "default.yaml"
```

See [`tiny_x_small_lm.yaml`](../templates/configs/tiny_x_small_lm.yaml)
for the minimal example, and
[`final.yaml`](../templates/configs/final.yaml) for the version that
combines this curriculum with the WSD-S scheduler and a higher LR.

## First-run download

The first time this config is materialised it downloads both source
datasets (~100GB+ for SmolLM-corpus, much smaller for Tiny Stories)
and tokenises them. Subsequent runs hit the on-disk cache and load
near-instantly. Downloads and cached tokenisations live under
`datasets/` at the repo root.

## Empirical result in the parent project

In the [`small-llm` 10x Chinchilla runs](../README.md#10x-chinchilla-runs),
swapping in this curriculum dataset (with all other knobs held to the
baseline) buys **~0.020 eval loss** vs the pure-SmolLM baseline (2.309
vs 2.329). The curriculum's effect on early/mid-training generation
quality is qualitatively larger - mid-training samples carry an
obvious children's-story register and produce coherent short
narratives noticeably earlier than the pure-SmolLM runs - but only the
eval-loss number is captured numerically, since the eval split is
SmolLM-only. See the parent README's `tiny_x_small_lm.yaml` section
for details.
