# DiLoCo: Work-Unit Dispatch (Design Proposal)

**Status:** proposal — not implemented.
**Owner:** TBD.
**Supersedes (when implemented):** the manual `--num-shards N --shard-index I`
flow in `examples/tiny_experiments/diloco/` and
`examples/base_lm_project/templates/configs/diloco.yaml`.

## Problem

DiLoCo workers currently partition the dataset by hand. Each worker is
launched with `--num-shards N --shard-index I`, and each worker's dataloader
calls `dataset.shard(N, I)`. Each worker is also assigned a unique output
directory (today: by mixing `shard_index` into the model name) so the
per-worker checkpoint and log streams don't collide.

This works but has several failure modes that matter more as we move toward
async / heterogeneous / elastic deployments:

- **Duplicate `--shard-index` silently doubles up training on the same
  rows**, biasing the global average. Two operators pointing at the same
  server with `--shard-index 0` is a common manual error.
- **`N` has to be fixed at launch.** A worker that joins late can't expand
  the partition; a worker that dies leaves its shard untouched until a
  restart of the whole cluster with a smaller `N`.
- **Static partition is wrong for async DiLoCo.** A worker that runs 4×
  faster than its peers chews through its 1/N slice and then either idles
  (sync) or keeps re-iterating the same data (async, without `dataset.shard`
  awareness) — both undesirable.
- **Per-worker output dir naming is an operator concern.** The
  `model_name + shard_index` convention is one workable answer; there are
  others, and the choice doesn't belong in user-facing config.

The DiLoCo implementation predates the **dataset server**, which now
provides arbitrary-row-range seeks (`/v1/datasets/{handle}/iter?position=N&limit=M`).
This unlocks a much better dispatch model: the DiLoCo server hands out
**work units** (deterministic slices of the dataset) as workers request
them, and workers stream the rows for the unit they were assigned from the
dataset server. Nothing has to be known in advance about worker count.

## Goals

1. Workers do **not** declare `num_shards` or `shard_index`. They just
   register with a DiLoCo server and ask for work.
2. Workers can join and leave at any time. A worker that dies loses **at
   most one work unit's worth of data** (which is automatically reissued
   to another worker).
3. Async DiLoCo, heterogeneous hardware, and elastic membership all "just
   work" without operator coordination.
4. The unique-per-worker output dir is generated by the DiLoCo server on
   register and used by the worker without further configuration.
5. Existing manual `--shard-index` configs keep working, gated by an
   opt-in flag. Migration is per-config.

## Non-goals

- Replacing the DiLoCo outer-loop algorithm (parameter sync, pseudo-grad
  averaging, outer optimizer). That stays as-is.
- Changing the dataset server's wire format. We add small endpoints; we
  don't restructure.
- Solving training-time data shuffling for non-`dataset_server` datasets.
  Phase 1 requires datasets served by a dataset server.

## Core concept: work units

A **work unit** is a deterministic, contiguous slice of a dataset,
identified by `(dataset_id, unit_id)`.

- `dataset_id` is a stable hash of the dataset's identity: the `load_args`
  the dataset server uses for that handle (path / HF id / config / split /
  revision / etc.), normalized and JSON-serialized. Two workers loading the
  same dataset compute the same `dataset_id` independently.
- `unit_id ∈ {0, 1, …, K − 1}`, where `K` is a fixed-per-dataset constant
  (default 1024; configurable). `K` should be large compared to the
  expected peak worker count so dispatch granularity is fine, but small
  enough that each unit is a meaningful slab of work (a unit becomes the
  natural inner-loop dataloader batch source, so very small units would
  add per-unit-request RPC overhead).

The mapping `unit_id → row range` is deterministic from `(unit_id, K,
dataset_length, optional_seed)`. The DiLoCo server only ever sees `unit_id`
values; the worker translates `unit_id → (position, limit)` against the
dataset server using existing endpoints. **Neither server needs to know
the other's internal data model.**

```
start = (unit_id      * length) // K
end   = ((unit_id + 1) * length) // K
limit = end - start
```

If shuffle is desired, the DiLoCo server includes a `shuffle_seed` in the
registration response; the worker passes it to
`/v1/datasets/{handle}/iter?seed=…&position=start&limit=…`. The dataset
server's shuffle is already deterministic in `seed`, so every worker sees
the same shuffle order and the unit-id → row mapping stays consistent.

## State ownership

| Component       | What it owns                                             |
|-----------------|----------------------------------------------------------|
| Dataset server  | Datasets themselves: `length`, `column_names`, content, shuffle. Existing endpoints. |
| DiLoCo server   | The work queue: per-dataset `(K, shuffle_seed)`, the set of `unit_id`s issued / completed / available, worker → currently-held unit mapping, per-worker output dir suffix. |
| Worker          | Its own training state. Translates `unit_id` to `(position, limit)` and streams rows from the dataset server. |

This split keeps the dataset server purely about data and the DiLoCo
server purely about coordination — neither has to grow knowledge of the
other.

## API surface

### DiLoCo server: new endpoints

```
POST /datasets/register
  body:  { dataset_id, hint: { length, source } }
  reply: { dataset_id, total_units: K, shuffle_seed, output_dir_suffix }
```

The first worker to call this for a given `dataset_id` causes the server
to allocate the work queue (`K` units, all in `available`) and snapshot
the dataset's length. Subsequent calls return the same plan; later
workers' `hint.length` must match (mismatch → 409 Conflict; the operator
shipped diverging dataset configs to different workers).

`output_dir_suffix` is a short stable string the worker appends to its
output directory (e.g. `"-w0"`, `"-w1"`). Allocated per-worker per-dataset
on first registration, persistent across reconnects.

```
POST /work/request
  body:  { worker_id, dataset_id }
  reply: { unit_id } | { exhausted: true, epoch: int }
```

Returns the next available `unit_id` and marks it as `issued_to_worker`
with a timestamp. If the queue is empty:
- (a) increment the dataset's epoch counter, regenerate `shuffle_seed`,
  refill the queue, and return the next unit.
- Or, depending on a per-dataset `multi_epoch` flag set at register time,
  return `exhausted: true` and let the worker decide whether to stop or
  re-register for another epoch.

```
POST /work/complete
  body:  { worker_id, dataset_id, unit_id }
  reply: { ack: true }
```

Marks the unit as `completed`. Idempotent; completing a unit that's
already completed (e.g. duplicate retry on flaky network) is a no-op.

```
POST /work/release
  body:  { worker_id, dataset_id, unit_id }
  reply: { ack: true }
```

Worker says "I'm not going to finish this — put it back". Used when the
worker is shutting down cleanly mid-unit (graceful stop, scale-down).

```
GET /work/status?dataset_id=…
  reply: {
    total_units, completed, available, in_flight, abandoned, epoch,
    by_worker: { wid: { current_unit, units_completed_this_epoch } }
  }
```

Diagnostic surface for the DiLoCo view and `forgather diloco status`.

### Dataset server: changes

**None required for phase 1.** The existing
`GET /v1/datasets/{handle}/iter?seed=&position=&limit=` already supports
exactly the slice semantics the worker needs.

Worth considering for phase 2 (optimization, not correctness): a
`/v1/datasets/{handle}/dataset_id` endpoint that returns the canonical
`dataset_id` for a handle, so the worker doesn't have to recompute the
hash from `load_args`. Small ergonomic win; skip until needed.

### Worker integration

Worker startup sequence:

1. `DiLoCoCallback._setup()` registers with the DiLoCo server (existing).
   Receives `worker_id` and initial global params.
2. **New:** worker fetches its dataset handle from the dataset server
   (existing `/v1/load`), computes `dataset_id`, and calls
   `POST /datasets/register` on the DiLoCo server. Receives `K`,
   `shuffle_seed`, `output_dir_suffix`.
3. Worker reconfigures its output dir to `<base>/<output_dir_suffix>` and
   creates a `WorkUnitDataset` iterable that wraps the dataset handle
   plus a reference to the DiLoCo server.
4. The trainer's dataloader iterates over the `WorkUnitDataset`. Internally
   it loops: `request → iter rows in (position, limit) → complete → request`.
5. The DiLoCo callback's outer-sync hook (the existing one that runs every
   `sync_every` optimizer steps) is unchanged; sync rounds happen
   orthogonally to work-unit boundaries.

`WorkUnitDataset` is a thin iterable; conceptually:

```python
class WorkUnitDataset(IterableDataset):
    def __iter__(self):
        while True:
            unit = self.diloco.request_work(self.dataset_id)
            if unit.exhausted:
                return  # epoch complete
            start, end = self._range_for(unit.unit_id)
            try:
                for row in self.ds.iter(seed=self.shuffle_seed,
                                        position=start, limit=end-start):
                    yield row
            finally:
                self.diloco.complete_work(self.dataset_id, unit.unit_id)
```

(Real impl needs to handle interruption / retry / heartbeat-on-unit
correctly — see "Fault tolerance" below.)

## Lifecycle scenarios

### Happy path (3 workers, sync)

- W0, W1, W2 all register against `dataset_id = D` with `K = 1024`.
- W0 asks for work → gets unit 0. W1 → 1. W2 → 2.
- Each iterates ~`length/1024` rows, calls `complete`, requests next.
- Continues until all 1024 units are completed.
- Server transitions to epoch 1: regenerates `shuffle_seed`, refills the
  queue. Next request returns unit 0 (with the new shuffle).

### Late worker

- W0, W1 are running, on units 47 and 52.
- W2 starts, registers, requests → gets next available (53).
- W2's training begins from the current global params (DiLoCo's existing
  dynamic-membership semantics).

### Worker dies mid-unit

- W0 holds unit 47, no heartbeat for `heartbeat_timeout` seconds.
- The DiLoCo server's existing health monitor evicts W0. As part of
  that eviction (extended for this design), unit 47 is moved from
  `in_flight` back to `available` (marked `abandoned_at` for telemetry).
- Next `/work/request` returns 47 to whoever asks next.
- Net data loss: 0 units. (W0 may have partially-processed 47 — that work
  is wasted, but it isn't lost to the global model since DiLoCo's outer
  optimizer only applies pseudo-grads from completed sync rounds.)

### Async DiLoCo, heterogeneous workers

- W_fast does ~10 units in the time W_slow does 1. The queue naturally
  routes more units to W_fast — no operator action required, no DyLU
  configuration required for *data balance* (DyLU still applies for sync
  frequency balance, but that's a separate concern).

### Multi-epoch

- Default: server auto-cycles epochs (refill on exhaustion). The DiLoCo
  callback's existing "stop after N optimizer steps / sync rounds" logic
  decides when the worker stops.
- Opt-out via `multi_epoch=false` at register time for runs that want
  exactly one pass; workers receive `{exhausted: true}` and exit their
  inner loop.

### DiLoCo server restart

- Work-queue state is persisted alongside global params + outer optimizer
  state in the server's checkpoint (extends the existing `save_state`).
- On restart, units that were `in_flight` (issued but not completed)
  become `abandoned` — they go back into the available pool. Workers
  reconnect, re-request, and resume.

### Worker dataset mismatch

- W1 registered with `dataset_id = D, length = 1_000_000`.
- W2 registers with `dataset_id = D, length = 1_000_500` (stale checkout).
- DiLoCo server returns 409: "dataset_id D was registered with length
  1000000; your hint disagrees".
- Operator-visible error rather than silent training on
  off-by-one-windowed shards.

## Fault tolerance summary

| Failure                | Behavior                                                                           |
|------------------------|------------------------------------------------------------------------------------|
| Worker dies mid-unit   | Heartbeat timeout → unit returned to queue → reissued to next requester. 0 loss.   |
| Network blip on request | Worker retries with exponential backoff (existing pattern in `DiLoCoClient`).     |
| Network blip on complete | Server marks complete on first ack; duplicate completes are no-ops.               |
| DiLoCo server restart  | Work queue restored from checkpoint. In-flight units become available.             |
| Dataset server restart | Worker's `iter` call retries (existing dataset_server client behavior).            |
| Worker restart         | Re-registers, gets fresh unit, training continues against current global params.   |

## Migration plan

Phase 0 (this doc, plus optional preparatory refactors):
- Land the design.
- Verify the dataset server's existing `iter?position&limit&seed`
  semantics are sufficient (looks fine from current code).

Phase 1: backend coordination
- Implement DiLoCo server endpoints: `datasets/register`, `work/request`,
  `work/complete`, `work/release`, `work/status`.
- Extend `DiLoCoServer.save_state` to include the work-queue state.
- Add tests covering issuance, completion, dead-worker reissue, epoch
  rollover, dataset_id mismatch.

Phase 2: worker integration
- Implement `WorkUnitDataset` in `forgather.ml.diloco`.
- Add `DiLoCoCallback._setup_work_dispatch()` that:
  - Loads the dataset handle, computes `dataset_id`.
  - Calls `datasets/register`, receives the plan + `output_dir_suffix`.
  - Rewrites `args.output_dir` to include the suffix.
  - Replaces the dataset with `WorkUnitDataset`.
- Gate behind `diloco_work_dispatch=true` (template variable / env var
  `DILOCO_WORK_DISPATCH=1`).

Phase 3: webui surface
- The training-submit DiLoCo radio gains a "Use work-unit dispatch"
  checkbox (default ON when the selected server supports it; OFF for
  back-compat with older servers).
- The DiLoCo view's status panel shows per-dataset work-queue progress
  (units complete / available / in-flight / abandoned).
- The legacy `num_shards` / `shard_index` dynamic args become hidden when
  work-unit dispatch is on.

Phase 4: deprecate manual sharding
- After Phase 3 has been exercised on real runs, mark
  `--num-shards`/`--shard-index` as deprecated in the worker CLI.
- Keep the code path around for at least one release for back-compat.

## Open questions

- **Output-dir suffix collision across DiLoCo servers.** Two DiLoCo
  servers running on the same machine using overlapping `output_dir`
  paths could in principle produce colliding suffixes for unrelated
  workers. We allocate suffixes per `(diloco_server_uuid, worker_id)`
  rather than just `worker_id` to keep this safe.
- **What if a worker holds many concurrent units?** Could be a
  performance optimization for high-throughput workers (request 4
  units, iterate them sequentially while the next request is in
  flight). Phase 5+ — start with 1-unit-at-a-time.
- **Validation / eval datasets.** Phase 1: each worker evaluates on the
  full eval set; the trainer averages metrics across workers (existing
  behavior). Eval is small and rarely needs sharding.
- **Multiple datasets per worker.** A worker training on a mixed corpus
  may have several datasets. Each gets its own register call and its
  own independent work queue. The `WorkUnitDataset` composes
  naturally — multiple instances, one per source dataset, mixed by the
  existing data-mixing layer.
- **`K` selection.** Default 1024 is a guess. Should it auto-scale with
  `length`? Probably: a tiny dataset (10k rows) with K=1024 means each
  unit is ~10 rows, which is silly. Reasonable rule: `K = clip(64,
  length / target_unit_rows, 4096)` with `target_unit_rows = 1024` or so.
  Bikeshed during impl.
- **Replay / determinism for debugging.** With the server allocating
  units, an exact-replay debugging mode would need the server to record
  the issuance order. That's an obvious extension; not phase 1.

## What this design intentionally does *not* try to solve

- Removing dataset_server as a dependency. Phase 1 *requires* the dataset
  server. In-process datasets keep the manual-sharding path.
- Replacing DiLoCo's outer-loop math (averaging, optimizer). Untouched.
- Cross-cluster dataset registration (peer A's DiLoCo server picking
  units assigned by peer B's). Single DiLoCo server per training group;
  cluster-mode aggregation in the webui is just for visibility, not
  cross-coordination.
- Solving streaming-DiLoCo (fragment sync) interactions. Fragment sync
  is per-parameter; work-unit dispatch is per-data. They're orthogonal
  and should compose without surgery.

## Acceptance criteria for the implementation

A run with this implemented should be observable as:

1. Start a DiLoCo server pointing at a model checkpoint and a dataset
   server reachable on the LAN.
2. Launch any number of workers (1, then 3, then 7, then kill 2) without
   any of them specifying `--num-shards` or `--shard-index`.
3. The DiLoCo view's per-dataset status shows units flowing from
   `available` → `in_flight` → `completed`, with the rate roughly
   proportional to each worker's `steps_per_second`.
4. Killing a worker results in its in-flight unit appearing in the
   abandoned counter briefly, then re-issued to the next requester.
   Training continues without intervention.
5. Total work completed matches `K × epoch` exactly — no row trained on
   twice within an epoch, no row missed.
